# lhg-solo-mvp：MVP 范围界定与技术选型

> 目标：把验证过的想法，砍成一份"2 周能上线"的 MVP 范围文档。
> 核心纪律：**没有"不做清单"的 MVP 不是 MVP，是愿望单。**

## 1. 何时使用

- 想法已通过 lhg-solo-idea 验证，准备动手时 → 必须先跑本 skill
- 做到一半发现范围膨胀、越做越多时 → 回来重跑第 3 步
- 只是改个小功能（1-2 天工作量）→ 不用跑，直接做

## 2. 输入与输出

- **输入**：验证过的想法（idea-brief.md，或一句话 + 验证结论）
- **输出**：`mvp.md`，包含：一句话产品、目标用户、P0 功能（≤5 个）、不做清单、2 周倒排、技术选型、验收标准、成功指标、风险

## 3. 砍范围四刀法（核心方法论）

### 第一刀：用户故事压缩

把所有"我想要"翻译成用户故事："作为 [谁]，我想要 [做什么]，以便 [得到什么]"。
然后只保留能回答这个问题的故事："如果只能解决一个问题，是哪一个？"
剩下的全部进"不做清单"——不是删除，是延期。

### 第二刀：手动冒充（Wizard of Oz）

每个功能问："上线第一周，我能不能手动替它干？"
能手动 → 第一版就手动（如人工审核、手动发邮件），代码以后再写。
一人公司的第一行代码应该写在"手动已跑通"之后。

### 第三刀：2 周倒排

从"2 周后必须上线"倒推：14 天 − 2 天缓冲 − 2 天落地页/定价页 − 1 天冒烟测试 = 9 天写代码。
9 天 / 每个功能 2 天 = 最多 4-5 个功能。超了就继续砍，不要"加班搞定"——
一人公司没有加班这个选项，只有"砍"这个选项。

### 第四刀：竞品减法

看竞品最火的 3 个功能，问自己："我的用户没有这 3 个，愿不愿意付钱？"
愿意 → 砍掉；不愿意 → 才是 P0。MVP 不是"竞品 lite 版"，是"一个问题的最佳解"。

## 4. 技术选型矩阵（一人公司专用）

按四个维度打分（每项 1-5 分），选总分最高的，不要选"最酷的"：

| 维度 | 说明 |
|---|---|
| 熟悉度 | 你闭着眼睛能写吗？不熟 = 上线后半夜出 bug 你修不了 |
| 全栈覆盖 | 一套代码/一套部署能覆盖 Web + 移动端吗？ |
| 免运维 | 数据库/鉴权/部署有没有托管方案？一人公司不配"运维"这个角色 |
| 冷启动成本 | 免费额度能撑到 1000 用户吗？ |

**默认推荐**：Web 优先选"全栈框架 + 托管数据库/鉴权"组合（如 Next.js + Supabase 类思路）；
需要移动端选跨端一套代码方案。**偏离默认必须写理由**，理由只能是"用户明确要求"或"核心功能默认栈做不了"。

### 4.1 必须输出的三项

1. 选了什么 + 为什么（对应上面四个维度的得分）
2. 备选方案（Plan B）：主方案卡住时的退路，一句话即可
3. 成本估算：域名 + 服务器/托管 + 第三方服务，首年总成本（精确到百元）

## 5. 任务拆分（2-5 天粒度即可）

一人公司不需要 2 小时粒度的任务板。拆到"2-5 天一个可交付"即可，每个任务写清：

- 做什么（一句话）
- 做完长什么样（可演示的标准）
- 依赖谁（没有依赖最好，有依赖标出来）

任务超过 7 个 → 回去继续砍。

## 6. 验收标准（Definition of Done）

每个 P0 功能一条验收标准，格式："[用户操作] → [可观察的结果]"。
例如："用户完成支付 → 收到开通邮件且账号升级为专业版"。
没有验收标准的功能 = 没做完，审计脚本 SOLO-MVP-006 会抓。

## 7. 砍范围实战案例

**案例**：番茄钟 App，初始想法有 12 个功能。

- 第一刀（用户故事压缩）：核心问题是"自由职业者专注被打断"，砍掉"成就徽章/排行榜"
  （解决的是"好玩"不是"专注"）。
- 第二刀（手动冒充）："专注统计报表"第一周手动做——用户截图发你，你手动回一张统计图，
  验证"用户真的会看报表"再写代码。
- 第三刀（2 周倒排）：9 天写代码 → 只剩"计时器/任务列表/统计"3 个 P0。
- 第四刀（竞品减法）：竞品 Forest 有"种树"，用户没它也愿意付 ¥19 → 砍。

最终 P0=3 个功能，不做清单 9 条，2 周上线。**不做清单全文**（示例）：

> 白噪音、主题换肤、数据导出、多端实时同步、成就徽章、排行榜、
> 番茄历史搜索、专注目标设定、社交分享——以上 v1 明确不做，任何"顺手加一个"
> 的需求先记入 v2 清单，本期不讨论。

## 8. 范围评审会（一人版，每周 15 分钟）

一人公司没有评审会，所以自己给自己开。每周对照 mvp.md 问三句话：

1. 本周做的功能在 P0 里吗？不在 → 停下来，挪到不做清单。
2. 有没有"顺手加的"？有 → 删掉或记入 v2，本周不许留。
3. 离上线日期还有几天？不够 → 砍一个 P0（只剩 3 个也行），绝不延期。

评审结论写进 mvp.md 末尾的"范围变更日志"，一行一条，诚实记录每次"没忍住"和"忍住了"。

> 合规提醒：MVP 文档如涉及支付接入、用户数据收集等表述，建议同步加上
> 通用合规声明（支付与税务合规因国家/地区而异，以当地法规为准），
> 审计脚本 SOLO-CMP-002/SOLO-CMP-005 会检查这一点。

## 9. 反模式（别踩）

1. **"第一版先做个大概"**：大概 = 永远做不完。第一版必须小而完整（能收钱）。
2. **技术尝鲜**：MVP 期学新框架，等于给产品上坟。
3. **"顺手加一个"**：每个"顺手"都是范围蔓延。想加 → 先写进不做清单，下期再议。
4. **完美主义落地页**：落地页 1 天搞定，产品才是本体。
5. **没有不做清单**：本文档最重要的一节就是"不做清单"，没有它，本文档作废。

## 10. 自检与反馈

### 10.1 质检门（每次使用后自查）

- [ ] mvp.md 有没有"不做清单"一节？没有 = 不合格。
- [ ] P0 功能 ≤ 5 个？超了必须砍或写理由。
- [ ] 2 周倒排里有没有留缓冲（≥2 天）？没有 = 计划作废。
- [ ] 技术选型写了"为什么"和 Plan B 吗？
- [ ] 有没有 TODO/待填占位符？有 = 文档没写完。
- [ ] 跑一遍 `python3 scripts/audit/indie_audit.py --target <文档目录>`，blocker 必须为 0。

### 10.2 标准冒烟用例

输入：`"番茄钟 App，验证结论：10 个自由职业者愿意付 ¥19/月"`
期望输出：mvp.md 包含 P0 ≤ 5 个功能、明确的不做清单、2 周倒排、
技术选型矩阵得分、每条 P0 功能的验收标准；审计脚本 0 blocker。
